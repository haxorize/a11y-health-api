# Axe payload validation lives in Pydantic at the API boundary

> **Amended by [ADR 0022](0022-error-contract-single-table-400-vs-422.md):** the boundary decision stands, but validation failures no longer surface as 422s — `parse_axe_payload()` wraps them into `InvalidAxePayloadError` (400, `invalid_axe_payload`) under the Error Contract.

> **Amended by #77:** "eliminated entirely" below overstated the outcome. The raw document kept crossing the service seam as a second argument (`raw_payload`, stored as the Page Result's Raw JSON) beside the validated Axe Payload, matched to it only by caller convention. #77 closed that side-channel: `parse_axe_payload()` is the single sanctioned crossing of the axe boundary, and it retains the exact uploaded document on the Axe Payload (`source_document`, a property backed by a private attribute, excluded from the schema's own serialization), from which the service reads the Raw JSON to store. *Retired by the 2026-09-04 amendment at the foot: once the crossing moved behind the service seam, the service holds the raw document itself.*

> **Amended 2026-08-05 (#134):** the crossing now runs behind the service seam (`create_page_result`'s first statement) and again in the CLI at scan load, and the boundary covers the identity fields `name` and `endTime`. The title and the body below describe the original placement; the dated amendments at the foot are the current record.

The axe DevTools JSON shape is fully validated by the `AxePayload` Pydantic schema at the API boundary, including semantic checks (impact values, classification tag shape, criteria parsing) — not just structural ones. The service layer receives a validated `AxePayload` and trusts it. A custom `InvalidAxePayloadError` previously raised from the service layer was removed (#55); validation failures surface as 422s through Pydantic's standard error path.

Considered and rejected:
- **Pass raw `dict[str, Any]` into the service and validate there**: the original shape (#25 replaced it). Forced every service helper to defensively re-check fields, scattered error formatting, and tempted callers to peek into unvalidated dicts. The `dict` path was eliminated entirely once the schema could carry the semantic rules.
- **Two-layer validation (Pydantic for shape, service for semantics)**: rejected because every "semantic" rule we had — impact must be one of four values, classifications must look like `{"standard": ..., "version": ..., "level": ...}`, wcag_criteria must parse — was expressible as a Pydantic validator. Splitting the rules across layers lost the locality without buying anything.

The boundary is now: outside the schema = unsafe input; inside the service = trusted, structured payload. New axe payload constraints belong on the schema.

## Amendments

**Amended 2026-08-05:** the boundary widens over the document's identity fields, and the crossing moves behind the service seam. `AxePayload` gains optional `name` and `endTime` — the two fields the CLI had been reading raw with hand-rolled checks — strict when present, absent-is-fine; the offset-less `endTime` UTC assumption moves into the schema's validator, which keeps today's parser so what parses today keeps parsing. `parse_axe_payload()` stays the sole sanctioned crossing, but its call site moves from the endpoint into `create_page_result`'s first statement, so the service owns its `invalid_axe_payload` error mode and its pending-run precondition (which moves in from the scan-run service, retiring the page-result service's only sibling-service import). This revisits "the service layer receives a validated `AxePayload`" deliberately: what the original decision rejected was validation *scattered inside* service helpers, and none of that returns — every rule stays on the schema, and below the crossing only the typed payload exists; the raw parameter has exactly one reader. The CLI consumes the same schema at scan load, dropping its raw reads — the one behavior change: a locally invalid file now fails before any upload, leaving no partial pending run; the left-pending rule survives for server-only rejections. No bypass flag: CLI and server ship from one package, so skew means a mismatched install, and the fix is reinstalling, not preserving the raw-upload side door. Rejected: a second, shallow crossing for just the identity fields (two sanctioned crossings where the module promises one), and widening without moving the crossing (the parse stays caller-remembered and the service still can't own its error mode). — amended: see Amendments 2026-09-12

**Amended 2026-09-04 (#134 review):** four corrections to the amendment above, each a decision taken on a review finding.

- **"The one behavior change" was three.** Moving the crossing into the CLI validates *every* file's `endTime` at load, where the old resolver parsed only the first file that carried one; a directory whose later file has an unreadable `endTime` failed nowhere before and fails at load now. The server narrowed too: the pages POST now returns `invalid_axe_payload` for a non-string `name` or an unreadable `endTime`, bodies it accepted with 201 before, and `openapi.json` cannot express that because the body is declared free-form — so the `contract-change` procedure does not fire and this paragraph is the record. And load-time failure is all-or-nothing for `import` as well as `ingest`: no date directory uploads if any file fails.
- **An empty-string `endTime` is absent, not unreadable.** "What parses today keeps parsing" is kept literally: the old loader read every falsy value as absent, so `""` falls back to the directory mtime. `0`, `False`, and any string `fromisoformat` rejects stay invalid — none ever parsed.
- **Every invalid file is reported at once.** `load_scan` collects schema failures instead of stopping at the first, and `import` collects across all date directories, so one re-run fixes everything (`InvalidScanFilesError`, plural). Decode failures (`MalformedScanFileError`) still stop at the first; a file that isn't JSON is rarer and usually a truncated export.
- **The no-bypass premise, restated.** "CLI and server ship from one package" was the wrong reason: the server at `--base-url` can be any version. The reason that holds is that the CLI runs the schema the server runs, so a file it refuses is one the same server version refuses; when versions differ the fix is matching them, and the message says so after telling the operator to fix the file first.

Two retirements ride along. `source_document` (the #77 mechanism) is gone: the service parses the raw document itself now, so the parameter it already holds is the Raw JSON to store, and the CLI keeps the decoded document beside the typed model in one `LoadedFile` record — the invariant #77 guarded is now unrepresentable rather than documented. And `AxePayload` drops `populate_by_name`: the document root accepts the axe spellings only, so a snake_case `end_time` key is an unmodeled key like any other rather than a second spelling that could fail the load.

**Amended 2026-09-27 (#177):** an axe rule's derived values are read after its fields are validated, and its help link must be a web address.

- **Where the derivation runs.** `AxeRule` takes `tags` as its only input for Category, WCAG Criteria, and Classifications. An after-validator reads all three from the validated tags in one call and keeps the result, and the rule exposes them as read-only properties. The alternative was cached properties over `tags`, rejected because a property is read at first use, and a rule with no known category tag has to be refused here, at the Axe Boundary. The before-validator it replaces read the tags before they were checked, so a `tags` value that was not a list of strings escaped as a bare `TypeError`: a 500 from the pages endpoint and a traceback from the CLI. The private `_tag_parsing.py` module is gone; its reading lives beside the rule.
- **Which messages change.** Two inputs get a new message, both on the existing `invalid_axe_payload` mode. A rule with no `tags` key reported `findings → violations → N: No category tag found` and now reports `findings → violations → N → tags: Field required`. A rule whose `tags` is a single string reported the same category message and now reports `… → tags: Input should be a valid list`. A null, a number, or a list holding a non-string, which raised before, now gets the framework's list or string error at `tags`. A rule with no category tag, or an unknown one, keeps its message byte for byte. — amended: see Amendments 2026-09-27 (#177 review)
- **The help link is refused, not emptied.** A non-empty `helpUrl` that does not start with `http://` or `https://`, in any letter case, is rejected as `helpUrl: must be an http or https address` through the existing `invalid_axe_payload` mode. An empty one is still accepted, since it is no link. Emptying a bad link was the alternative, the safer one if real exports carried relative links; the one tracked export carries only `https:` links, so refusing won. Archived exports outside the repo were not checked. A CLI load is all or nothing per date directory, so one relative link fails its whole directory until the link is fixed. — amended: see Amendments 2026-09-27 (#177 review)
- **The page's file name waits on a product answer.** `testSubject.fileName` is named a file by axe and served as the Page Result's `url`, so whether it takes the same check depends on whether the product treats it as a URL. It stays unchecked until the product decides. — amended: see Amendments 2026-09-27 (#177 review)

The published contract is unchanged: the pages body is free-form in `openapi.json`, so none of these narrowings can be declared there.

**Amended 2026-09-27 (#177 review):** four corrections to the amendment above, each taken on a review finding.

- **A category message keeps its bytes only when the rule has no other fault.** The after-validator runs once every field has passed, so a field fault now wins where the category message used to. A rule with no category tag and no `impact` reported `findings → violations → N: No category tag found` and now reports `findings → violations → N → impact: Field required`; a rule with an unknown category tag and a `nodes` value that is not a list now reports `… → nodes: Input should be a valid list`. The same holds for any other field fault beside a missing or unknown category tag.
- **The help link must be a lowercase `http://` or `https://` address with a host.** "In any letter case" is withdrawn: the UI's guard in `../a11y-health-ui/src/lib/help-link.ts` renders a link only behind a lowercase scheme, so `HTTP://x.test/r` was stored here and shown there as no link, and it is now refused. A link with no host, such as `https://`, and a link holding whitespace or a control character are refused as well. The message and the `invalid_axe_payload` mode are unchanged.
- **A bad help link fails the whole `import`, not its own date directory.** `import` loads every date directory before the first upload and raises once for all of them, as the 2026-09-04 amendment says, so one relative link stops every directory from uploading until it is fixed. `ingest` loads a single directory, so there the cost is that directory.
- **`fileName` is not the only upload text left unchecked.** Entries under `passes` and `inapplicable`, including their `helpUrl` values, and a node's `html` and `target` are stored verbatim in the Raw JSON, and `html` and `target` are served on the Rule Finding as text; nothing screens any of them for a link scheme. No operation in `openapi.json` serves the Raw JSON. Only the typed rules' `helpUrl` is checked, because it is the only one of them the UI renders as a link.

## Deferred

- Checking `testSubject.fileName` as a web address, reopened when the product decides whether a Page Result's `url` is a URL or a file name.
- Checking the operator's archived exports for relative help links, which decides whether refusing stays or emptying replaces it. The check is a search of the archived export directories for `"helpUrl": "` values not starting `http`, and it reopens the refusal only if it finds any.
