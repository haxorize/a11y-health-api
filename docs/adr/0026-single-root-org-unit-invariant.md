# Single-root Org Unit invariant, enforced by the database

The Org Unit hierarchy is a tree, not a forest: at most one parentless Org Unit (the Root Org Unit) exists per deployment, because portfolio-level views and the Org Unit Rollup assume a single apex — with two roots the UI Overview silently rendered the lowest-id one (#92). A forest was rejected because nothing consumes a second root and every consumer would forever need to answer "which root is the portfolio?"; relaxing tree → forest later is cheap, while the reverse is a data remediation. Enforcement follows the Dependents Guard convention: a partial unique index on `parent_id IS NULL` is the source of truth (a service-only guard was rejected for the check-then-insert race), with the service raising the declared `duplicate_root` mode (409) on both `POST /org-units` and `PATCH /org-units/{id}`; the migration pre-checks existing data and fails with the offending ids rather than auto-reparenting, so no org structure is rewritten implicitly. — amended: see Amendments 2026-09-26

## Amendments

- **2026-09-12 (#146)** — This record says at most one Root Org Unit exists and never says where one comes from: the first one is seeded by migration `3737c72ff7ef` (`seed_org_unit_humana`) under `migrations/`, and production mints one thereafter too: `create_org_unit` calls `_check_no_other_root` and then builds the row whenever `parent_id` is omitted, and `update_org_unit` promotes an existing node the same way when the field is sent null (`services/org_unit.py:37-46` and `:74`). That is what makes the `duplicate_root` guard above meaningful rather than decorative. An earlier draft of this entry claimed the migration was the only site, having derived the negative from a search for `parent_id=None` — a spelling neither production path uses, so the check was green exactly where the hole was.
- **2026-09-26 (#163)** — "A tree" is what the index and the reparent guard enforce, not a state the code may assume. Two concurrent reparents can each pass the cycle check and commit a cycle between them, the known gap #176 carries. The walks over the hierarchy and the Org Unit Rollup therefore stop at a committed cycle instead of recursing forever: the subtree read deduplicates with `union`, the ancestor read carries a `CYCLE` clause, and the rollup keeps a visited set, so a cycle yields a partial answer rather than a hang or a 500. — amended: see Amendments 2026-09-27 (#176)
- **2026-09-27 (#176)** — The concurrent-reparent gap is closed: every reparent takes one tree-wide advisory lock before it reads the unit, so two of them can no longer commit a cycle between them ([ADR 0047](0047-one-tree-advisory-lock-serializes-reparents.md)). The walks and the rollup keep their cycle guards, since a cycle committed before that lock, or written by something other than the app, still reaches them.
