# Per-owner advisory locks serialize rollup recomputes

The #98 uniqueness indexes only decide same-observation races; two rollups for one owner deriving *different* observation times never collide on a row, so a recompute holding a stale children view could prune and displace a newer committed Score Snapshot (#101). Each rollup therefore acquires a transaction-scoped Postgres advisory lock keyed per owner (`rollup:{owner_type}:{owner_id}`, hashed to a bigint) as its first statement, so the children read and the prune/insert sit under one serialization; the indexes remain the backstop for same-observation races (`concurrent_rollup`, 409, retryable).

Rejected: **detect-and-fail** (compare-then-abort is unsound under READ COMMITTED — the check itself races without serialization underneath) and **SERIALIZABLE isolation** (blast radius across all mutating operations, plus the suite-wide retry orchestration #98 scoped out).

Lock ordering: single-chain triggers (scan-run completion and deletion, app deletion) traverse in one direction — an org unit's hierarchy upward, then the brand lock last — so their locks are acquired leaf-to-root in a consistent order and they cannot deadlock among themselves. Two triggers run *two* cascades in one transaction — app reassignment and org-unit reparenting (old subtree, then new) — so the second chain starts back at a leaf while the transaction already holds locks up to the shared root. Such a transaction can deadlock not only with a crossing twin but with *any* concurrent single-chain rollup climbing the second subtree (e.g. an ordinary scan-run completion); a reparent committed mid-cascade can likewise reorder ancestry between in-flight transactions. Postgres detects every such cycle and resolves it by failing one transaction — an accepted outcome, no worse for the data than the pre-lock race. The loser currently surfaces as an unhandled 500 (the error contract maps only domain errors); mapping `deadlock_detected` into the retryable 409 contract is tracked as #104.
