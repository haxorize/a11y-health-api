# Per-owner advisory locks serialize rollup recomputes

> **Amended by [ADR 0047](0047-one-tree-advisory-lock-serializes-reparents.md):** a PATCH that carries an Org Unit's `parent_id`, null or unchanged included, takes one tree-wide advisory lock before anything else, so the lock order below gains a lock ahead of the rollup locks. It adds no deadlock outside the hash collision ADR 0047 describes, because no transaction waits on the tree lock while holding a rollup lock. Reparents now run one at a time, so the clause below on a reparent committed mid-cascade reordering ancestry is retired between two reparents and still holds between a reparent and any other cascade, such as a Scan Run completion, which does not take the tree lock.

> **Amended by [ADR 0048](0048-scan-run-row-lock-serializes-completion-and-page-adds.md):** a status PATCH on a Scan Run and the creation of a Page Result in it lock the Scan Run row before their checks, the status PATCH locks its App before that, and an App deletion locks the App's Org Unit and then the App, so the lock order below gains row locks ahead of the rollup locks: the Org Unit, then the App, then the Scan Run. App and Org Unit updates lock their row at the load, and ADR 0048 gives the whole order, the tree lock included. The Scan Run lock is stronger than the one the status UPDATE took, and it widened a deadlock between completion and App deletion, which App deletion also had with Org Unit deletion; the two earlier locks close both. The cascades below still take key-share locks on the Org Units they write snapshots for after their rollup locks, but only Org Unit deletion conflicts with those, and it takes no rollup lock, so no cycle runs through the rollup locks.

The #98 uniqueness indexes only decide same-observation races; two rollups for one owner deriving *different* observation times never collide on a row, so a recompute holding a stale children view could prune and displace a newer committed Score Snapshot (#101). Each rollup therefore acquires a transaction-scoped Postgres advisory lock keyed per owner (`rollup:{owner_type}:{owner_id}`, hashed to a bigint) as its first statement, so the children read and the prune/insert sit under one serialization; the indexes remain the backstop for same-observation races (`concurrent_rollup`, 409, retryable).

Rejected: **detect-and-fail** (compare-then-abort is unsound under READ COMMITTED — the check itself races without serialization underneath) and **SERIALIZABLE isolation** (blast radius across all mutating operations, plus the suite-wide retry orchestration #98 scoped out).

Lock ordering: single-chain triggers (scan-run completion and deletion, app deletion) traverse in one direction — an org unit's hierarchy upward, then the brand lock last — so their locks are acquired leaf-to-root in a consistent order and they cannot deadlock among themselves. Two triggers run *two* cascades in one transaction — app reassignment and org-unit reparenting (old subtree, then new) — so the second chain starts back at a leaf while the transaction already holds locks up to the shared root. Such a transaction can deadlock not only with a concurrent move the opposite way between the same two subtrees but with *any* concurrent single-chain rollup climbing the second subtree (e.g. an ordinary scan-run completion); a reparent committed mid-cascade can likewise reorder ancestry between in-flight transactions. Postgres detects every such cycle and resolves it by failing one transaction — an accepted outcome, no worse for the data than the pre-lock race. The loser's `deadlock_detected` (40P01) is translated at the lock-acquisition statement — where a victim's error always lands — into the retryable `concurrent_rollup` 409 (#104); any other driver error propagates unchanged, as in ADR 0028. — amended: see the ADR 0047 note above
