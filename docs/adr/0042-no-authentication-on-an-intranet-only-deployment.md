# No authentication or authorization, on an intranet-only deployment

Every operation the API serves mounts without authentication or authorization, by decision rather than by omission. All 31 operations across 21 paths under `/api/v1/` take a database session and nothing else; no route or router carries a `dependencies=` gate, `openapi.json` declares no `securitySchemes` and no operation-level `security`, no auth library is a dependency, and the interactive docs at `/docs` and `/redoc` serve ungated. The ten mutating operations are exactly as open as the reads: anything that can reach the port can create, rename, or delete an App, an Org Unit, or a Scan Run.

The assumption this rests on is that the deployment is reachable from the corporate intranet and from nowhere else, with no route in from outside it. That assumption is the whole of the security posture, and it is not enforced by anything in this repository — no code here can tell whether it holds. [ADR 0001](0001-bigint-identity-pks.md) already leans on the same premise when it rejects UUIDs for an internal-only service, but it records the premise as context for a key-type decision and never decides the posture itself. This record is where the posture is decided, so a reader who wonders why a delete needs no credential finds an answer rather than an oversight.

The allowed-origin list is the only browser-side boundary. `ALLOWED_ORIGINS` defaults to `http://localhost:3000`, the sibling UI's dev server, and a model validator rejects the `*` wildcard unless `DEBUG` is on, so a production misconfiguration fails at startup rather than serving every origin. That boundary stops a page on another origin from reading responses in a colleague's browser. It stops nothing else: it is not an access control, and a direct client that is not a browser never consults it.

Credentials are not part of the boundary, because the API issues none. There is no cookie, no session, and no token, so a browser has nothing to attach and `allow_credentials` grants nothing today. The flag is nevertheless set to `True` in `main.py`, which permits credentials that do not exist and would quietly start mattering the day one does. Whether to set it to `False` now is [#186](https://github.com/haxorize/a11y-health-api/issues/186)'s, along with the engine and pool values; this record fixes only that credentials are outside the boundary as decided.

Considered and rejected: an API key or single sign-on in front of every route. A rational team picks it the day a route reaches beyond the intranet, and it is the right answer then. It loses today because it would buy nothing the network boundary does not already provide, while adding a secret to distribute to every operator running the onboarding CLI and a login to an internal tool whose entire dataset is org-chart structure, tracked web-property metadata, and axe DevTools accessibility results for public marketing pages. None of that is personal or member-facing data; there is no user, member, or subscriber table, and no column naming a person.

Its cost, which is real: the day the assumption stops holding, there is no partial position to retreat to, because nothing distinguishes a read from a delete or one caller from another. The migration is not a flag but a new layer.

Revisit when: any route becomes reachable from beyond the intranet, or a cookie or session is added to the API, or member-facing or otherwise non-public data enters the dataset — most likely by scanning an authenticated screen, since `PageResult.raw_json` and `NodeFinding.html` persist rendered markup as uploaded and the payload boundary validates shape, not sensitivity.
