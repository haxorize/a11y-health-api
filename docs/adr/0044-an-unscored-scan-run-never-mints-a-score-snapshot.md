# An unscored Scan Run never mints a Score Snapshot

A Scan Run that has not been scored produces no Score Snapshot, and both halves of the system enforce that rather than one. The server refuses the Pending to Completed transition for a run holding zero Page Results, raising `EmptyScanRunError` as a 409 with code `empty_scan_run`. The onboarding CLI, when any page upload fails, skips the completion request entirely and leaves the run Pending with an instruction to fix the inputs, re-ingest, and then delete the abandoned run. Decided 2026-07-07 across two commits, `c640a82` for the server half and `98fc269` for the CLI half.

The incident is what makes this worth recording, because the obvious behavior is the one that shipped first and was wrong. The CLI completed a run unconditionally, so a total upload failure completed an empty run; the server guarded only the status transition, so it computed an app score over zero pages. The result was a 0.0 Score Snapshot, which read "no data" as "everything critical", and because Score Snapshots roll up, that zero propagated into every ancestor Org Unit mean and every Brand mean. A reader who finds the refusal without the incident sees a guard against something that cannot happen; the point is that it did.

Three options were weighed. Score the subset is what the CLI was doing, and it makes a run's score depend on which page uploads happened to succeed, which is not a property of the site being measured. Score zero is what the server was doing, and it conflates absence of evidence with evidence of total failure, at the one place in the model where the difference matters most. Refuse is what was taken: an unscorable run stays in the only state that honestly describes it, and the operator is told what to do about it. The cost is that a partial ingest leaves a Pending run behind that somebody has to delete, which is why the CLI's message carries the run id.

Two properties of the shape are easy to misread. First, Scan Run Status has exactly two values, Pending and Completed, with Pending to Completed the only valid edge and Completed terminal. There is no failed or partial state, so Pending is not merely where an unscorable run lands, it is the only place it can land. Second, the server's refusal sits at a single seam, `update_scan_run_status` in `services/scan_run.py`, and not at the mint site: `compute_app_score` and `on_scan_run_completed` will mint for any Scan Run handed to them, as the test factories do directly. That is deliberate, since completion is the one door into scoring, but it means the invariant is a property of that door rather than of the scoring service.

This record owns when a Score Snapshot is not minted. [ADR 0015](0015-score-snapshot-append-only.md) owns what a snapshot is once minted, and [ADR 0027](0027-score-snapshot-raw-counts-only.md) owns which columns it carries; neither speaks to the refusal.

Revisit when: scoring a partial ingest is put on the roadmap, which would replace the refusal with a subset score and need a way to mark a snapshot as covering part of a run.
