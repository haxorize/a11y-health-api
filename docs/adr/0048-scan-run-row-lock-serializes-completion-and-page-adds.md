# Row locks serialize Scan Run completion, Page Result creation, and App and Org Unit writes, and an Org Unit foreign-key race maps to not-found

This amends [ADR 0029](0029-per-owner-advisory-lock-rollup-serialization.md) by placing row locks ahead of its rollup locks. It also amends [ADR 0024](0024-existence-guard-core-module-two-tier-rule.md) by making the Existence Guard's single raise site a single construction site, so the Integrity Guard can raise the not-found error the guard builds when a write names an Org Unit deleted underneath it. It also sets one lock order for every write that locks an Org Unit, an App, or a Scan Run, and moves the App and Org Unit updates' row locks to their load. The filename keeps its original slug, which the records that link here name.

`update_scan_run_status` checks the transition in Python and then writes the status. Under READ COMMITTED, two concurrent completions of one Pending run both pass that check. The second status UPDATE waits on the first's row lock, proceeds once it commits, and its App Score Snapshot insert violates `uq_score_snapshot_scan_run_id`, which surfaces as an undeclared 500 (#178). `create_page_result` has the same shape: its status check reads a Pending run, so a Page Result created mid-completion lands on a Completed run with no Page Health and is never scored.

Completion therefore reads the Scan Run with `SELECT … FOR UPDATE`, and Page Result creation reads it with `FOR SHARE`, each before its status check. A second completion waits, reads Completed, and fails with the existing `InvalidStatusTransitionError`, 409 `invalid_status_transition`. A Page Result created mid-completion waits and fails with the existing `ScanRunCompletedError`, 409 `scan_run_completed`. Neither is retryable, because a retry reads the same Completed run and gets the same answer. Concurrent Page Result creations share the lock and still run together. No error mode is added, so the contract does not move.

These locks are not the old ones moved earlier. `FOR UPDATE` is stronger than the `FOR NO KEY UPDATE` the status UPDATE took, and the `FOR SHARE` on Page Result creation is new: before, that write took only the `FOR KEY SHARE` of its foreign-key check, which the status UPDATE does not block. The stronger lock widened a cycle that already existed between the status UPDATE and App deletion. App deletion locks the App row and then, through its cascade, waits on the Scan Run, while completion holds the Scan Run and its App Score Snapshot insert takes `FOR KEY SHARE` on the App. Executed, the two deadlocked, and the 40P01 surfaced as a 500, since only the rollup lock maps one. App deletion deadlocked the same way with Org Unit deletion: its rollup's Org Unit Score Snapshot insert takes `FOR KEY SHARE` on the App's Org Unit, while Org Unit deletion holds that unit and waits on the App in its dependents check.

Completion therefore locks its App before it locks the Scan Run, in `FOR NO KEY UPDATE`, the mode an App move loads its row with, rather than the `FOR KEY SHARE` its snapshot insert takes. Under `FOR KEY SHARE` a completion runs beside an uncommitted move, rolls up the unit the App left from the committed view, and the move's rollup of the unit it joins cannot see the new App Score Snapshot, so that unit stays stale. The cost is that completions of different runs of one App, and a completion and a move of its App, run one at a time. Scan Run deletion takes the same App lock first, for the same reason. App deletion takes `FOR KEY SHARE` on the App's Org Unit, which conflicts only with that unit's deletion, so updates of the unit still run beside it; it then locks the App `FOR UPDATE` while the App is still in that unit, so a move in flight is waited out and the rollup reads the unit the App ended up in. An App deletion that finds the App moved locks the unit it is in now and tries again, and one behind another deletion of the same App finds it gone and gets the declared 404 `not_found`. Lock order: ADR 0047's tree lock, then the Org Unit, then the App, then the Scan Run row, then ADR 0029's per-owner rollup locks, which every cascade takes after its writes. App deletion follows that order whole, and completion and Org Unit deletion each follow a part of it, so whichever of two conflicting writes comes second waits. A completion behind an App deletion finds its run gone and gets the declared 404 `not_found`. An Org Unit deletion behind an App deletion gets its declared 409 `has_dependents`, or deletes the unit if nothing depends on it any more; ahead of the App deletion, it is refused at once, since the App it finds holds no conflicting lock. An App deletion whose Org Unit is deleted while it waits, after the App moved out of it, locks the unit the App is in now. No error mode is added.

An App update that sets `org_unit_id`, and an Org Unit update that sets any field, load their row with `FOR NO KEY UPDATE`, the lock their UPDATE takes anyway, moved to the load. Unlocked, an update behind a delete of its row waited at the UPDATE, matched no row, and raised an unmapped `StaleDataError`, a 500. An App move behind another move of the same App read the owner from before the first move committed, and rolled up the unit the App was in before the first move instead of the unit it left. Locked at the load, the second write reads the row after the first commits: a deleted row gets the declared 404 `not_found` from the Existence Guard, and a moved App rolls up the unit it actually left. The mode is unchanged, so no new conflict arises: `FOR NO KEY UPDATE` does not block the `FOR KEY SHARE` of Org Unit deletion's dependents check, and between the load and the UPDATE the updates take no other lock. An App move still locks the App before its rollup's Org Unit Score Snapshot inserts lock the old and new units, as it did before. An update with nothing to write locks nothing, and can still return a row a concurrent delete is about to remove; it does not read the row again, so a delete that commits after its load does not fail it.

After the rollup locks, the cascades' Org Unit Score Snapshot inserts still take `FOR KEY SHARE` on each ancestor they write. Only Org Unit deletion conflicts with that, and it takes no rollup lock. It checks child units first, then Apps, then Score Snapshots, so a deletion of a unit a cascade is climbing through finds a live child unit or App and is refused before it can wait on a Score Snapshot row the cascade replaced. That is reasoned, not executed, and it rests on the order Postgres fires the three foreign-key triggers, which is by trigger name: measured on the per-run test schema and on a migrated database, and pinned by no test.

The line between this lock and the Integrity Guard (ADR 0028) is what decides the race. The guard answers a race a constraint decides, such as a write that references an Org Unit deleted underneath it, which #178 maps to `NotFoundError` at the App and Org Unit write sites. The Existence Guard builds that error for the mapping, which amends [ADR 0024](0024-existence-guard-core-module-two-tier-rule.md)'s single raise site into a single construction site. A check-then-act on a row's own state has no deciding constraint: the snapshot uniqueness violation is a side effect several calls past the check, and nothing catches the Page Result race at all. That kind of race takes a row lock.

Considered and rejected:

- **Mapping `uq_score_snapshot_scan_run_id` through the Integrity Guard:** the loser rewrites Page Health and attempts a snapshot before it is refused, the guard has to wrap the whole scoring and rollup call, and its 409 infers a status nobody read. It also cannot close the Page Result race, since no constraint is violated there.
- **A conditional UPDATE on `status = 'pending'`:** it takes the same row lock, but at the write, so the transition check and the empty-run check read state no lock holds. Locking at the read makes every check see the state the write acts on.

Revisit when: a Scan Run gains a second status transition, a code path takes a rollup lock and then writes a Scan Run, an App, or an Org Unit, or a write other than a delete takes `FOR UPDATE` on an App or an Org Unit.
