# Scan Run creation rejects an offset-less `scanned_at`, unlike the Axe Boundary

`POST /apps/{app_id}/scan-runs` refuses a `scanned_at` with no UTC offset: `ScanRunCreate.scanned_at` is declared `AwareDatetime`, so the request fails Pydantic validation and returns the framework 422 with `["body", "scanned_at"]` as the error's location. Decided 2026-10-02 in the grill [#179](https://github.com/haxorize/a11y-health-api/issues/179) asked for.

Before this, the field was a bare `datetime`. An offset-less value passed validation and reached the `timestamptz` column as a naive instant, which stored it shifted by the server's UTC offset; the 2026-09-05 audit's finding P1-S02 confirmed that live. One Scan Run posted with an offset and again without one therefore stored two instants, and since `scanned_at` becomes the Observation Time of its App's Score Snapshot, the two would rank differently in Latest Score Snapshot selection and in the history's keyset order.

Two fixes were weighed. Assuming UTC, as `parse_end_time` does, would have rejected nothing a caller sends today and made every door agree. It was not taken because it turns a caller who meant local time into a silent wrong instant, the very failure being fixed, with the error moved from the server's offset to the caller's. Rejecting was taken because the contract already says so: the field is published as `format: date-time`, which is RFC 3339, and RFC 3339 requires the offset. Nothing on the wire changes, so `openapi.json` and the UI's generated client are unchanged; the server now enforces the offset the spec has always promised. It is not a full RFC 3339 check: Pydantic's lax mode still reads a Unix timestamp, sent as a number or a numeric string, as UTC, and accepts an offset written without its colon (`-0400`). Neither stores a wrong instant, so the field stays lax rather than taking strict mode's contract change for callers who send numbers.

The asymmetry with the Axe Boundary is deliberate. The boundary reads an offset-less axe `endTime` as UTC in `parse_end_time`, because there the timestamp is axe's own, inside a document a scanner wrote, and the only alternative to assuming UTC is refusing a real Axe Payload over a field we do not control. A client posting a Scan Run is writing to our contract, and can be held to it.

The regression accepted: a caller outside this workspace posting offset-less timestamps, or a bare date such as `2026-04-01`, which was read as naive midnight, now gets a 422 where it got a 201. None is known. The two callers in the workspace both send an offset, the CLI through `create_scan_run` in `cli/_client.py` and the UI's e2e seed through `tests/e2e/helpers/seed.ts`. The deployment is intranet-only ([ADR 0042](0042-no-authentication-on-an-intranet-only-deployment.md)), with the CLI as the documented way in ([README](../../README.md#cli)). The 422 names the field, so an unknown caller finds out on its first request and fixes it by adding an offset, rather than storing wrong instants nobody sees.

Rows stored before this change are not corrected. A stored `scanned_at` does not record whether it arrived without an offset, so no backfill can tell a shifted row from a correct one, and both known callers have always sent an offset. Whether any deployed database holds a shifted Scan Run, and with it a shifted App Score Snapshot `snapshot_at`, was not checked: no deployed database was reachable when this was decided.

This record owns the rule for a client-supplied `scanned_at`. [ADR 0009](0009-axe-payload-pydantic-boundary.md) owns the Axe Boundary, including its UTC assumption; [ADR 0022](0022-error-contract-single-table-400-vs-422.md) owns why this refusal is a framework 422 with no domain code.

Revisit when: a caller that cannot send an offset turns up, which would need the assume-UTC rule here too, or a second client-supplied timestamp is added, which should follow this rule unless its source is a document we do not control.
