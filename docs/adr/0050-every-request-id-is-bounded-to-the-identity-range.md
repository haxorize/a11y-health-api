# Every request id is bounded to the identity range at the schema

Every id a request carries, whether a path parameter, a request body field or a query filter, is bounded to 1 through 2**63 - 1, the range of a PostgreSQL `bigint` identity. An id outside it fails request validation and returns the framework 422. Decided 2026-10-10 in the grill that [#180](https://github.com/haxorize/a11y-health-api/issues/180) asked for.

Before this, ids were bare `int`. An id at or past 2**63 passed validation, reached asyncpg, and overflowed the `bigint` parameter as a 500; the 2026-09-05 audit's finding P1-S06 confirmed that live on `GET /apps/{id}`, `GET /brands/{id}` and `POST /apps` with `brand_id`. The keys are `BigInteger` identities ([ADR 0001](0001-bigint-identity-pks.md)), so the ceiling is the column's own, and the bound is defined once in `core/` rather than spelled at each site. A cursor's id values arrive encoded rather than as a field, so `core/pagination.py` holds them to the same range, and a forged one outside it is the 400 `invalid_cursor` the cursor contract promises ([ADR 0017](0017-keyset-pagination-deep-module.md)).

The floor is the part a reader will question. A ceiling alone was weighed, and it would have kept `GET /apps/0` and `GET /apps/-1` answering 404 as they did before. It was not taken because an identity column starts at 1, so 0 and a negative id can never name a row, and that is a fact about the request's shape the schema can state rather than a lookup that misses. Under [ADR 0022](0022-error-contract-single-table-400-vs-422.md), input the framework's validation can refuse is its 422, so the floor puts these ids with the other shape failures. The regression accepted: a caller sending 0 or a negative id gets 422 where it got 404. Two callers take ids a person types. The UI refuses one below 1 itself, since a URL can carry 0 or a negative id, and shows not-found rather than the API's 422 (a11y-health-ui af9352f0). The `a11y` CLI forwards them to the API: `--parent-id` on `org-units create`, and `--org-unit-id` and `--brand-id` when `import` creates the App, since an existing App ignores them. A 0 or a negative id there now prints the framework's 422 where it printed a coded 404.

The rule is held by a test, not by review. `tests/test_id_bounds.py` walks the application's OpenAPI document and fails on any request parameter, or request body property at any depth, named `id` or ending in `_id` that lacks `minimum: 1` and `maximum: 9223372036854775807` or carries no integer at all, and it holds its own walk honest with a known hit. It compares a parameter's bounds exactly and a body's as doubles, because FastAPI's OpenAPI `Schema` model types `minimum` and `maximum` as floats: a request body schema publishes the ceiling as `9.223372036854776e+18`, which is 2**63, while a parameter keeps the exact integer. Validation is exact either way, and a double-precision JSON reader, the UI's codegen among them, reads both spellings as the same number; restoring the integer would mean overriding the framework's document, which was weighed and not taken. A new endpoint that declares an id as a bare `int` turns that test red. Response fields stay unbounded, because a bound on a read validates nothing a client sends.

**2026-10-19 — a cursor value the API would misread is refused.** Decided in the grill that [#183](https://github.com/haxorize/a11y-health-api/issues/183) asked for. An id must be a JSON integer, and a timestamp must be an ISO string that carries a UTC offset. Before this, the coercion took whatever the cursor held. A non-finite float, whether `Infinity`, `-Infinity` or a literal past the double range such as `1e400`, raised `OverflowError`, which nothing caught, so it returned 500. `1.5`, `1.0`, `true` and `"5"` were read as ids 1, 1, 1 and 5. A timestamp with no offset was read in the API process's time zone and bound as a shifted instant, because asyncpg converts a naive `datetime` to UTC through `astimezone`. That conversion also overflowed into a 500 for a timestamp at the edge of the range, such as `9999-12-31T23:59:59-14:00`, so the decode now converts to UTC itself and refuses one that overflows. Two narrower closures were weighed. Rejecting the non-finite constants at JSON decode would have missed `1e400`, which Python parses as a float rather than as a constant. Catching `OverflowError` alone would have closed the 500s and kept the silent misreads. A broader check was weighed too: re-encode the decoded values and refuse any cursor that does not match `encode_cursor`'s output byte for byte. It was not taken, because it also refuses a forged timestamp such as `2026-01-01T00:00Z`, which names the instant it is read as. The regression accepted: an id that is not a JSON integer, or a timestamp without an offset, returns 400 where it returned a page or a 500. Apart from those two kinds, the non-finite floats and the timestamps at the edge of the range, every cursor keeps the status it had. No issued cursor carries one, because the encoder has written raw integers and offset-carrying ISO strings since cursor pagination began in `b6cb9bb`, and a client never constructs a cursor. [ADR 0049](0049-scan-run-creation-rejects-an-offset-less-scanned-at.md) holds a request's `scanned_at` to the same offset, refused as the framework 422, because that field is validated by the schema; a cursor is decoded after validation, so its refusal is the cursor contract's 400. Revisit this entry when a keyset type other than `int`, `datetime` or `str` is added, since it needs its own rule for what the API would misread.

Revisit when: a key type other than a `bigint` identity is introduced, such as a UUID, or a caller turns up that needs 0 or a negative id to mean something.
